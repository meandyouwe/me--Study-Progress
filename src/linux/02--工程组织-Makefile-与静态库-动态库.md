# 2. 工程组织：Makefile 与静态库、动态库

一个工程只要超过两个源文件，手敲 `gcc` 就会失控。Makefile 解决的是「增量编译 + 依赖描述」，库解决的是「代码复用 + 二进制交付」。

## （一）四种赋值符号

Makefile 的赋值符号差异全在「展开时机」，这是最容易混淆的一组语法：

| 符号 | 名称 | 展开时机 | 典型用途 |
|---|---|---|---|
| `=` | 递归赋值 | 使用时才展开 | 依赖后续变量定义的场景 |
| `:=` | 立即赋值 | 定义时立刻展开 | 绝大多数情况，行为可预测 |
| `?=` | 条件赋值 | 仅当变量未定义时赋值 | 允许命令行覆盖默认值 |
| `+=` | 追加赋值 | 追加到已有值之后 | 累加源文件列表、编译选项 |

```make
CC      := gcc
CFLAGS  := -Wall -O2
CFLAGS  += -g                  # 追加调试信息
SRCS    := 1.c 2.c
TARGET  ?= app                 # 命令行 make TARGET=test 可覆盖

$(TARGET): $(SRCS)
	$(CC) $(CFLAGS) -o $@ $^
```

> 易错点：命令行必须以 **Tab** 开头，四个空格会报 `missing separator`。这是新手第一个 Makefile 必踩的坑。

## （二）静态库

静态库在链接期把用到的目标代码「复制」进可执行文件。

```make
libmy.a: 1.o 2.o
	ar rcs $@ $^

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

app: main.c libmy.a
	$(CC) main.c -L. -lmy -o app
```

- `ar rcs`：`r` 替换或插入、`c` 创建、`s` 生成索引（没有索引链接会慢且可能失败）。
- `-L.` 指定库搜索路径，`-lmy` 对应 `libmy.a`（**去掉 `lib` 前缀和扩展名**）。
- 产物特点：体积大（代码被复制），但部署简单，不依赖外部 `.a`。

## （三）动态库

动态库在运行期加载，多个进程共享同一份代码段。

```make
libmy.so: 1.c 2.c
	$(CC) -fPIC -shared -o $@ $^

app: main.c libmy.so
	$(CC) main.c -L. -lmy -Wl,-rpath,'$$ORIGIN' -o app
```

- `-fPIC`：生成位置无关代码，动态库**必须**加，否则链接报 `relocation R_X86_64_32 against ... can not be used`。
- `-shared`：产出共享对象。
- 运行时找不到库的三种解法：`export LD_LIBRARY_PATH=.`（临时）、`-Wl,-rpath`（编译期写入）、放入 `/etc/ld.so.conf.d/` 后 `sudo ldconfig`（系统级）。

| 对比项 | 静态库 `.a` | 动态库 `.so` |
|---|---|---|
| 链接时机 | 编译链接期 | 程序启动/运行时 |
| 可执行文件体积 | 大 | 小 |
| 库更新 | 必须重新编译程序 | 替换 `.so` 即可生效 |
| 启动速度 | 快 | 略慢（需重定位） |
| 部署 | 单文件即可 | 需保证库路径可被找到 |
| 内存占用 | 每进程一份 | 多进程共享代码段 |

> 扩展 · 排查手段：`nm -D libmy.so` 看导出符号，`ldd app` 看运行时依赖，`readelf -d app | grep RPATH` 看运行路径。三个命令能定位 90% 的「库找不到 / 符号未定义」问题。

## （四）头文件与库的边界

库对外只暴露头文件：`.h` 放函数声明、类型定义、宏；`.c` 放实现。调用方 `#include "my.h"` 并链接 `-lmy`。若头文件在子目录，编译时补 `-I./include`。

> 易错点：把变量定义写进头文件，多文件包含时链接报 `multiple definition`。正确做法是头文件里写 `extern int g;`，在**一个** `.c` 里写 `int g = 0;`。C99 起的 `inline` 变量规则更细，工程上仍建议沿用 `extern` 方案。
